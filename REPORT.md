# Artist estimate parity — one shared component, same send path, permission-gated

Same repo, new session. "Artists entering estimates get a reduced experience vs. staff, and artist submission doesn't trigger the real generate-and-send flow." Four parts.

## Part 1 — Investigation

Three separate estimate-entry surfaces existed, all editing the same `Inquiry` fields but drifted apart:

- **Staff Generate & Send Estimate** and **staff Revise Estimate** (both `InquiryDetail.tsx`) already shared `SessionBreakdownEditor.tsx`'s per-session pieces (`SessionHoursRows`, `SessionCountField`, `suggestSessionPrice`), but each hand-rolled its own copy of the *top-level* fields one layer up: flat-rate checkbox, hide-duration checkbox, the single-session hour/price fields, and all the seed/validate/submit logic around them.
- **Artist Approve** (`MyInquiries.tsx`, `PATCH /inquiries/:id/respond`) was a separate, much smaller 4-field form: plain `<input type=number>` hour fields (no `HOUR_OPTIONS` selects), no flat-rate toggle, no session count, no multi-session planning, no rate auto-suggestion (the artist's own `hourlyRateCents`/`flatRateCents` weren't even in the API projection backing this page). Its submit called `PATCH /respond`, which did a bare `prisma.inquiry.update` setting `status: AWAITING_CLIENT_RESPONSE` — moving the pipeline stage forward while **never** mints a token, reconciles `PlannedSession`, or contacts the client. The inquiry looked "sent" in the UI without anything having been sent.

## Part 2 — One shared component

New `apps/web/src/components/EstimateFieldsEditor.tsx`: a controlled `EstimateDraft` value object (`isFlat, showDurationToClient, sessionCount, hoursMin/Max, priceLow/High, sessionRows`) plus pure helpers (`emptyEstimateDraft`, `estimateDraftFromInquiry`, `computeEffectiveEstimate`, `estimateDraftToRequestFields`, `estimateDraftToSessionsPayload`, `validateEstimateDraft`) and the presentational component itself, wrapping `SessionBreakdownEditor`'s existing per-session pieces together with the single-session top-level fields the three contexts used to each duplicate by hand. All three call sites (`InquiryDetail.tsx`'s send-estimate widget, its Revise Estimate modal, and `MyInquiries.tsx`'s Approve modal) now own one `useState<EstimateDraft>` and render `<EstimateFieldsEditor value={} onChange={} assignedArtist={} lockedSessions={}>` — a genuine single component, not a copy per context.

Artist rate auto-suggestion needed `hourlyRateCents`/`flatRateCents` added to two places that never carried them for an artist's own view: backend `ARTIST_INQUIRY_SELECT` (`routes/inquiries.ts`, scoped safely — this projection is only ever the caller's *own* assigned inquiries, so an artist sees only their own rate, never another artist's) and the frontend `Inquiry.assignedArtist` type in `MyInquiries.tsx`.

`CurrencyInput.tsx` gained a `disabled` prop (needed for `EstimateFieldsEditor`'s locked-session display, didn't exist before).

## Part 3 — Same send path, permission-gated

Extracted `POST /:id/send-estimate`'s entire body (status/assignment guards, `sessions[]` validation, effective-price computation, `PlannedSession` reconciliation, token minting, real-SMS auto-send via `getOrCreateClientConversation`/`sendClientSms`) into `apps/api/src/lib/estimates.ts`, mirroring the `generateAndSendDepositForm` precedent (`lib/deposits.ts`) exactly — a lib function the route calls, not route logic a second caller reaches into. Split into `generateAndSendEstimate` (the real send) and `saveEstimateDraft` (validates and reconciles the exact same fields but never mints a token or contacts the client), sharing one `validateEstimateInputs` so a "saved, not sent" draft can never contain anything staff's own send path would have rejected. `POST /:id/send-estimate` itself is now a thin wrapper.

New permission key `inquiries.artistSendEstimate` ("Artists can send estimates directly"), added to `PERMISSION_KEYS`/`DEFAULT_ROLE_PERMISSIONS[ARTIST]` (backend) and `PERMISSION_GROUPS` (frontend) — **default TRUE, a judgment call**: an artist who can already enter their own estimate (`inquiries.enterEstimate`, already default-TRUE) triggering the same real send that action's own UI already implied was happening is a small step past an existing capability, not a new one, and today's actual behavior (moving to `AWAITING_CLIENT_RESPONSE` without contacting the client) was already the more surprising half.

`PATCH /:id/respond`'s APPROVE branch now checks `hasPermission(inquiry.studioId, Role.ARTIST, "inquiries.artistSendEstimate")` — **the project's studio, not the caller's own `req.user!.studioId`**, the same guest-artist scoping class fixed repeatedly in prior sessions; this key's check would have had the exact same failure mode if left on the caller's home studio. ON calls `generateAndSendEstimate` (identical response shape to staff's route: `estimateUrl`, `estimateSendResult`, 201). OFF calls `saveEstimateDraft` and returns a plain 200 with no `estimateUrl` — status deliberately stays `ARTIST_ASSIGNED` (not `AWAITING_CLIENT_RESPONSE`) since nothing was actually sent to the client yet; front desk's existing Estimate section on the same Inquiry page needs no new UI to review/send it.

**Found and fixed in passing** (same function, materially safer to fix now than leave): the DECLINE branch and the old bare-APPROVE branch both logged audit entries and broadcast `emitInvalidation` under `req.user!.studioId` instead of `inquiry.studioId` — for a guest artist, this would log to the wrong studio's audit trail and never live-refresh the actual project studio's connected staff. Also: `saveEstimateDraft`'s validation applies the same `ESTIMATE_REVISION_ONLY_STATUSES` gate as sending — without it, an artist could still silently rewrite a converted project's top-level price fields around Revise Estimate's deliberate "requires a reason" control, even with direct-send permission off.

New derived task source `apps/api/src/lib/tasks/artistEstimateNeedsReview.ts` (`ARTIST_ESTIMATE_NEEDS_REVIEW`), registered in `registry.ts`: matches `status: ARTIST_ASSIGNED, assignedArtistId: not null, estimateSentAt: null, priceEstimateLow: not null` — the last condition being exactly what `saveEstimateDraft`'s own validation guarantees is never null on a successful save, distinguishing "an estimate was actually entered and saved" from the ordinary pre-estimate state every inquiry passes through anyway. Naturally scoped to front desk by the existing `tasks.viewQueue` gate (default true FRONT_DESK, false ARTIST) with zero code changes needed there.

## Part 4 — Verification

**Automated regression** (`apps/api/src/routes/estimateParity.test.ts`, real Prisma/real HTTP, no mocking — same convention as `artistMobility.test.ts`): permission ON sends for real (token minted, status moves, `estimateUrl` returned); permission OFF saves without sending (no token, status unchanged, no `estimateUrl`); the derived task lists the saved-not-sent inquiry; an artist with the key off still gets 403 hitting the staff-only `POST /:id/send-estimate` directly (gated by the unrelated `inquiries.sendEstimate` key, unaffected either way); front desk sends the artist-prepared draft through the ordinary route and the task disappears. All 5 pass; full suite (both test files) 36/36.

**Live browser, permission ON** (`artist1@dev-studio.test`, real dev DB): Approve modal renders full parity (flat-rate checkbox, session count, hour selects) — confirmed by first accidentally proving multi-session works too (a wrong selector index bumped session count to 2, and the shared `validateEstimateDraft` correctly blocked submission client-side: "Session 1 needs an hour range," no request sent, no partial mutation). Entering 2–3 hours auto-suggested $300 at this artist's real $150/hr rate. Submitting: real 201, `estimateSentAt`/`estimateToken` set, status `AWAITING_CLIENT_RESPONSE`, a real `Conversation` row created (no `Message` row, since this dev studio has no SMS integration connected — `sendClientSms` correctly reports `not_connected` before ever reaching Twilio, identical to what staff's own pre-existing send already does here).

**Live browser, permission OFF**: toggled "Artists can send estimates directly" off for the ARTIST row via the real Team → Permissions UI as owner (screenshotted before/after — label, description, and default state all render correctly; "Permissions updated" confirmed the save). A second artist (`artist2@dev-studio.test`) approving at that studio hit an unrelated pre-existing issue — `inquiries.view` was already overridden `false` there from an earlier, unrelated test session, 403'ing the whole My Inquiries page — so the actual OFF verification used `artist1@dev-studio.test`'s own studio (a clean override there instead). Submitting: modal closed exactly like the ON case (no visible difference to the artist), but the DB shows the save-only path — fields saved (4–6hrs → $600–900 at $150/hr), `status` stayed `ARTIST_ASSIGNED`, no token. The derived task then listed it; a real HTTP call as that studio's OWNER to `POST /:id/send-estimate` sent it for real (201, `estimateUrl` present, the artist's own $600/$900 numbers carried through untouched), and the task disappeared afterward.

**Staff regression**: opened a real ARTIST_ASSIGNED inquiry's Estimate section as `owner@dev-studio.test` — same shared component, same validation message pre-fill (`Price and time ranges are required...`), filled 2–4 hours (auto-suggested this artist's own $85/hr rate correctly), clicked Generate & Send Estimate — real 201, status moved, price landed correctly. **Revise Estimate** (a real converted `SCHEDULING` project with an existing $200 flat estimate) opened with zero console/page errors and correctly seeded the flat-rate checkbox and existing $200/1hr values from `estimateDraftFromInquiry`'s planned-session branch — not submitted (no need to mutate a shared project's real state further for a render-only check).

## Judgment calls

- `inquiries.artistSendEstimate` defaults **TRUE** — flagged above; the alternative (default FALSE) would mean every studio silently loses the "estimate actually sends" behavior the artist-approve flow's UI already implied it had, on a feature whose entire point is closing that exact gap.
- OFF-path status stays `ARTIST_ASSIGNED` rather than any new intermediate status — avoids adding schema/enum surface for what's fully expressible as "no plan changed, nothing sent yet."
- The front-desk task is derived (queried live), not a stored row — matches this codebase's one and only system-task convention (`lib/tasks/`), no exceptions needed.
- Fixed the `req.user!.studioId` → `inquiry.studioId` audit/broadcast bug in `/respond` while already rewriting that function, rather than filing it separately — same root cause class as the new permission-check code sitting three lines below it.
